# 온라인 대전 설계 — 1대1부터 3대3까지

작성: 2026-10-27 · 상태: **최초 확정 설계 원본**. 1대1 첫 공개는 [v0.9.8 기록](23-online-duel-implementation.md), 이후 사용자가 변경한 육성 능력치·대전방·Elo는 [v0.10.0 기록](24-online-rooms-and-ranking.md)을 따른다. 아래 균등 능력치 결정은 최초 구현 당시의 이력이다.

## 1. 목표와 결정

**Render Free에서 온라인 1대1을 먼저 검증하고, 같은 경기·통신·계정 구조를 3대3으로 확장한다.**

사용자 확정: 자동 매칭, 기존 선수 외형, 균등 능력치, 온라인 성장 보상 없음. Godot 4.7.2 Standard / GDScript / Compatibility와 기존 농구 동작을 유지한다. 최초에는 사람 2명, 이후 사람 6명이 각각 자기 선수 한 명을 조작한다.

아래 시간·전송량·수용량은 구현 시작값과 검증 목표이며 실측값이나 보장값이 아니다. 1대1은 매칭뿐 아니라 판정·재접속·종료까지 검증한 뒤 공개한다. 3대3은 패스·다인 경합·팀 화면까지 검증해야 한다.

## 2. 현재 소스에서 해결할 경계

| 확인한 구조 | 필요한 변경 |
| --- | --- |
| game.gd가 입력·AI·카메라·포즈·공·점수를 함께 갱신하며 직접 조작/HUD는 players[0]을 전제한다. | 입력 수집, 공통 경기 실행, 화면 표현을 분리한다. 자기 슬롯이 1이나 5여도 카메라·조작·승패가 맞아야 한다. |

이번 설계에서는 다른 작업으로 수정 중인 경기·모션 코드를 변경하지 않았다. project.godot의 4.7 / GL Compatibility와 문서의 4.7.2를 확인했으며 엔진 실행 검사는 하지 않았다. 구현 때 Linux 서버 export template과 바이너리도 4.7.2인지 확인한다.

## 3. 서비스 구성

~~~mermaid
flowchart LR
  P[GitHub Pages] -->|게임·리소스| B[브라우저 Godot]
  B -->|기존 로그인·선수·참가권| S[Supabase court-rush API]
  B <-->|WSS 입력·경기 상태| G[Render 접속·자동 매칭]
  G -->|참가권 소비·결과 저장| S
  G <-->|컨테이너 내부 통신| M[Godot headless 경기 실행기]
  S --> D[(기존 cr_* 및 온라인 자료)]
~~~

### Render Free

- 코트러시용 **Free Web Service 하나**의 Docker 컨테이너에 Node 게이트웨이와 Godot headless 실행기 하나를 둔다. 다른 앱 서비스와 코드를 합쳐 재배포하지 않는다.
- Node는 HTTP 준비 확인·WSS·인증·대기열·방 배정·프로세스 감독을 맡는다. Godot가 농구 이동·접촉·공·난수·점수를 계산한다. 농구 규칙을 JavaScript로 다시 구현하지 않는다.
- 공개 PORT 하나에서 Node가 0.0.0.0으로 HTTP/WSS를 받는다. Godot와는 127.0.0.1 내부 TCP로 통신하며 프레임 길이·room ID·프로토콜을 검증한다.
- Godot는 서버 전용 Linux export/진입 씬으로 실행한다. 경기마다 전체 게임 프로세스·코트 메시·음원을 새로 만들지 않고 독립 경기 상태를 생성한다.
- 첫 시험은 **동시 경기 1개**. 이는 성능 측정 결과가 아니라 초기 제한이다. 빈 수용 슬롯이 없으면 대기하고, 측정 후 여유가 있을 때만 늘린다.
- 지역은 공식 제공 목록의 싱가포르를 첫 후보로 시험한다. 한국 이용자의 RTT와 실제 플레이로 판단한다.
- 두 프로세스와 필요한 접촉 자세 계산이 Free 자원에 들어가는지 첫 기술 검증에서 측정한다. 실패하면 공개 전에 계산 비용·수용량·호스팅 선택을 재검토한다.

### Supabase

기존 아이디·복구 코드·계정·선수·의상·성장 저장을 계속 쓴다. Neon 우선 검토 기준은 확인했으나 사용자는 기존 Supabase 유지와 Render 시험을 선택했다. 인증/DB 이관은 실시간 경기 추가의 선행 조건이 아니므로 이번 범위에 넣지 않는다.

| 제안 테이블명 — 아직 생성하지 않음 | 최소 내용 |
| --- | --- |
| cr_online_tickets | 참가권 해시, 계정·세션, 모드·호환 버전·서버 대상, 만료·소비 시각 |
| cr_online_matches | 경기 ID, 서버 실행 ID, 모드·규칙 버전, 시작/종료, 팀 점수·종료 이유·저장 상태 |
| cr_online_participants | 경기별 계정·팀·고정 슬롯, 검증된 외형 스냅샷, 이탈 기록. 경기별 슬롯/계정 중복 제약 |

대기열·실시간 경기 프레임은 Render 메모리에 두고 DB에 매 틱 쓰지 않는다. 참가권 만료 자료는 정리하고 진단용 경기 기록은 초기 30일 보관하는 안으로 시작한다. 계정 삭제 시 개인 연결·참가권 자료도 삭제/비식별화하도록 기존 삭제 경계를 검증한다.

새 테이블은 RLS와 역할별 최소 GRANT/RPC 권한을 같은 마이그레이션에 정의한다. 브라우저 직접 쓰기는 막고 API가 검증한다. 기존 ttk_*와 공유 Auth 설정은 바꾸지 않는다.

## 4. 사용자 흐름

1. **온라인 → 1대1 → 상대 찾기.** 미로그인은 기존 아이디 로그인, 선수가 없으면 기존 생성 화면으로 안내한다. 진행 중 로컬 경기를 바꾸기 전 종료 안내를 따른다.
2. **서버 준비 중.** 온라인을 선택했을 때만 Render 준비 요청을 보낸다. 다른 앱에서 경험한 15~20초는 참고이며 코트러시 기동 시간은 따로 측정한다.
3. **참가권 발급·WSS 인증.** 서버 준비 이후 참가권을 발급한다. 연결·버전·프로필 검증까지 끝나야 대기열에 넣는다.
4. **상대 찾는 중.** 경과 시간과 취소를 제공한다. 처음에는 동일 서버 지역·규칙·프로토콜 이용자를 대기 순서대로 묶는다. 예상 대기 시간·랭크 점수는 임의로 만들지 않는다.
5. **상대 발견 → 준비 → 3초 카운트다운.** 초기 스냅샷을 모두 로드했는지 확인한다. 15초 준비 제한 초과 시 예약을 취소하고 남은 이용자는 기존 대기 순서를 살려 다시 찾는다.
6. **경기 → 결과 → 다시 찾기.** 재도전은 새 대기 요청이며 종료된 방에 다시 들어가지 않는다. 온라인 보상 청구는 없다.

서버 준비 재시도는 2·4·8초 간격에 작은 무작위 차이를 두고, 총 90초 후 실패와 수동 재시도를 제공한다. 기동 중 HTML·503·타임아웃을 경기 API JSON으로 오인하지 않는다. 취소 후 늦게 도착한 응답은 무시하고 연결/대기 예약을 정리한다.

화면 상태는 idle → waking → authenticating → queued → reserved → loading → countdown → playing → reconnecting/ended. cancelled, unavailable, version_mismatch, aborted는 명시적 종료 상태다. ko/en/ja/zh, 키보드 초점·터치·모바일 회전을 함께 검증한다.

## 5. 인증·중복 매칭·재접속

### 일회용 참가권

- career.js가 기존 refresh/세션 처리로 새 online-ticket 동작을 요청한다. Edge Function은 auth.getUser, cr_session_valid, 코트러시 계정·선수 소유권을 검증한다.
- 60초 유효한 암호학적 난수 참가권을 발급하고 원본 대신 해시만 저장한다. 모드·규칙/프로토콜·서버 배포 대상에 묶는다.
- 참가권은 WSS 첫 인증 메시지로 보내며 URL/localStorage/분석·오류 로그에 넣지 않는다. 연결 후 5초 안에 인증을 끝내지 않으면 종료한다.
- Render는 온라인 서버 전용 비밀값으로 online-redeem을 호출한다. Edge가 참가권/세션을 재검증하고 트랜잭션에서 한 번만 소비한다. 검증된 계정·외형 자료를 반환한다.
- 소비 요청 ID로 서버 재시도를 멱등 처리하되 다른 요청·실행 ID에서의 재사용은 거부한다. 소비 응답은 클라이언트에 그대로 전달하지 않는다.
- Supabase service_role 전체 키를 Render에 복사하지 않는다. 전용 서버 비밀값은 참가권 소비·자기 실행 ID의 경기 등록/세션 검사/결과 저장에만 사용하고 웹/앱 번들에는 넣지 않는다.
- 참가/재접속과 진행 중 30초 단위 배치 검사로 세션 철회를 확인한다. 실제 무효와 검증 API 장애를 구분한다.

### 대기열과 연결 경쟁

계정당 queued/reserved/playing 점유는 하나다. 두 번째 탭이 기존 경기를 강제로 끊지 않는다. 한 Render 실행기의 상태 머신이 서로 다른 계정과 방 정원을 원자적으로 예약한다. 비동기 DB 작업 뒤 예약 세대 번호를 재확인해 이미 취소된 이용자를 시작시키지 않는다.

queue.cancel은 서버 최신 상태로 응답한다. 카운트다운 전에는 예약을 해제하고 시작 후에는 경기 떠나기 규칙을 쓴다. 모든 종료 경로에서 계정 점유와 방 슬롯을 반납한다.

재접속은 새 참가권과 메모리상의 기존 경기 예약을 확인해 원래 슬롯으로만 복귀시킨다. 새 연결 수락 시 이전 연결 세대를 폐기한다. serverEpoch가 바뀌면 이전 방에는 들어갈 수 없다.

향후 다중 인스턴스에서는 전역 대기열·계정 lease·방 라우팅이 필요하다. 단일 Free 인스턴스의 메모리 잠금을 그대로 복제하지 않는다.

## 6. 1대1부터 공유할 경기 모델

~~~text
MatchConfig: mode, teamSize, maxPlayers, rulesVersion, profileVersion,
             gameSeconds, shotClockSeconds, targetScore
MatchState: matchId, serverEpoch, tick, phase, phaseRevision, rngState,
            teams[], players[], ball, possessionRevision, eventSequence
PlayerState: slotId, teamId, connectionGeneration, position, velocity, facing,
             action, actionTick, cooldowns, contactPose, inputState
BallState: phase, ownerSlotId or null, shooterSlotId, lastTouchSlotId,
           position, velocity, flight, possessionRevision
~~~

teamId·slotId·로그인 계정 ID를 구분한다. 팀을 slot/3으로 추론하지 않는다. 1대1도 teamSize=1, maxPlayers=2인 두 팀 경기로 실행한다. 모드 차이는 설정·규칙 어댑터에 두고 입력·소유권·점수·접속을 공유한다.

### 균등 프로필 제안

서버의 online-standard-v1을 적용한다. 초기안은 모두 190cm의 동일 체격·도달 높이·속도·도약·슛·수비·기술 단계다. 기존 레벨·훈련·의상이 성능을 바꾸지 않는다. 체격을 그대로 두면 블록/리바운드 차이가 나므로 온라인 표시 모델도 공통 체격에 맞춘다. 이는 저장된 원본 선수의 키·능력치를 바꾸는 것이 아니다.

얼굴·헤어·모자·상의·하의·신발·색상은 소유권이 확인된 기존 장착 상태로 경기 입장 때 고정한다. 의상 부피는 충돌이나 팔 길이를 바꾸지 않는다. 모든 계정의 기술 사용 조건도 같게 한다. 3대3 최초 시험 역시 동일 프로필이며 G/F/C별 차등 표준 프로필은 이후 별도 밸런스 단계다.

### 경기 규칙의 첫 안

| 항목 | 온라인 1대1 | 온라인 3대3 |
| --- | --- | --- |
| 인원 | 실제 사람 2명 | 실제 사람 6명 |
| 기본 시간/공격 제한 | 90초 / 15초 | 180초 / 18초 |
| 승리 | 11점 선취 또는 종료 시 높은 점수 | 동일 |
| 동점 | 다음 득점 승리, 연장 최대 60초 후 무승부 | 동일 |
| 공격권 | 득점 후 상대, 수비 확보 후 외곽 클리어 | 동일 |
| 최초 공격 | 서버가 두 팀 중 공정한 난수 선택 | 동일 |
| 조작·보상 | 자기 선수 고정, 성장 보상·공개 순위 없음 | 동일 |

종료 전 릴리즈한 슛은 결과가 정리된 뒤 종료한다. 연장 상한은 무한 점유 방지를 위한 온라인 신규 제안이며 기존 AI 경기에는 적용하지 않는다.

## 7. 판정·입력·동기화

서버만 이동 한계, 슛 준비/릴리즈/확률, 블록·스틸·리바운드, 소유권·아웃·클리어·시간·득점·종료를 확정한다. 클라이언트는 의도만 보내며 점수·공 위치·소유자·스탯을 직접 지정하지 못한다. 경기별 RNG는 서버에서 관리하고 미확정 슛 결과를 미리 전송하지 않는다.

| 항목 | 초기 설정 |
| --- | --- |
| 경기 실행 | 고정 60Hz. 네트워크 메시지 수신 횟수와 독립 |
| 입력 | 이동/유지 30Hz, 누름·놓음 사건 즉시. sequence/사건 ID로 중복 제거 |
| 상태 전송 | 전체 스냅샷 20Hz, 소형 JSON으로 시작 |
| 화면 | 상대·공 100ms 보간 버퍼. 렌더 FPS와 경기 틱 분리 |
| 자기 이동 | 공통 규칙으로 예측, 마지막 서버 확인 입력 이후를 재적용해 보정 |
| 주요 사건 | 서버 tick·event ID·possessionRevision으로 득점/캐치/소리 중복 방지 |
| 연결 검사 | 연결 중 ping 10초, 응답 없음 15초부터 이상 판정하는 안 |

카메라 기준 입력은 클라이언트에서 코트 좌표로 변환하고 서버가 정규화한다. 조작 슬롯은 인증된 연결에 고정한다. 클라이언트가 임의 선수 ID를 지정해도 권한이 생기지 않는다.

슛의 누름·유지·놓음을 구분하고 같은 전송 간격 사이의 짧은 입력도 보존한다. 타이밍 보너스는 첫 버전에서 서버 적용 틱으로 계산한다. 클라이언트 시각으로 과거 슛/블록을 자유롭게 되돌리지 않으며 RTT별 체감 검사 뒤 제한된 보정 범위를 검토한다.

250ms 이상 입력 갱신이 없으면 이동/유지 상태를 중립화한다. 키업 유실로 무한 이동·무한 슛 준비가 생기지 않게 한다. 짧은 행동 사건은 연속 상태 덮어쓰기로 지우지 않는다. 메시지 크기·초당 행동 수·sequence·유한한 수치 범위를 검사한다.

WSS/TCP의 순서 보장 때문에 오래된 상태가 밀릴 수 있다. 아직 보내지 않은 스냅샷은 최신 하나로 교체하고 주요 사건은 순서를 보존한다. 이미 TCP에 들어간 자료는 취소할 수 없으므로 누적 버퍼가 계속 커지면 재동기화/재접속한다. 오래된 이동 명령을 뒤늦게 전부 실행하지 않는다.

### 접촉 자세 모듈이 선행 조건

공통 ContactPose가 릴리즈점·양손 캐치·블록 손바닥/방향·몸/발 접점을 제공한다. 서버와 화면은 같은 모션 정의·행동 틱을 읽고 서버만 메시·재질·소리를 생략한다. 필요한 리그/클립 계산은 서버 export에도 남긴다.

스킨을 제거하고 기존 대체 팔 좌표로 돌리면 표시 손과 다를 수 있다. 실제 모션의 서버/표시 손·공을 대조한 뒤 코어 분리를 통과시킨다. 손 접촉을 큰 구체 충돌로 임의 대체하거나 Free CPU 예산 때문에 판정 범위를 조용히 바꾸지 않는다.

## 9. 끊김·이탈·서버 장애 정책의 첫 안

| 상황 | 처리 |
| --- | --- |
| Esc/메뉴·탭 숨김·앱 전환 | 자기 입력 해제·음소거/메뉴. 서버 경기와 시계 유지. 복귀 때 전체 상태를 받아야 조작 재개 |
| 짧은 끊김 | 원래 슬롯 20초 유예, 새 참가권으로 재접속. 과거 입력 폐기 |
| 1대1 장기 이탈 | 서버와 상대가 정상이면 20초 후 이탈패. 명시적 떠나기는 즉시 기권. 둘 다 끊기거나 서버 장애면 무효 |
| 3대3 장기 이탈 | 초기 시험은 20초 후 경기 무효. 몰래 AI로 교체하지 않음. 팀 기권/AI 대체는 후속 설계 |
| 인원 부족 | 대기 유지·취소. AI로 부족 인원을 채우지 않음 |
| Render/worker 재시작 | 새 serverEpoch. 이전 실시간 경기 복원 없이 무효. 오래된 방 재입장 거절 |
| 과부하 | 신규 배정 중지·혼잡 안내. 서버 지연을 사용자 이탈패로 처리하지 않음 |
| 결과 저장 실패 | 결과 표시와 저장 지연 안내를 구분. 제한 재시도 후 미저장 상태, 성장/순위에 사용하지 않음 |

연결만 살아 있는 무입력은 별도로 45초 후 경고, 추가 15초 후 이탈 처리하는 안을 시험한다. 단순 ping이나 shoot 유지로 활동 시간을 늘리지 않는다.

정상 업데이트는 신규 매칭을 닫고 진행 경기를 마치는 수동 drain 뒤 배포한다. 플랫폼 강제 종료에는 충분한 유예가 있다고 가정하지 않는다. 미종료 DB 기록은 실행 ID/heartbeat로 무효 정리하고 이전 실행기의 늦은 결과 쓰기를 차단한다. 영구적인 서버 재시작 후 경기 복원은 첫 버전에 포함하지 않는다.

## 10. 단계별 구현과 통과 조건

| 단계 | 구현 내용 | 통과 조건 |
| --- | --- | --- |
| A. 공통 코어 | 입력·화면에서 판정 분리, headless ContactPose, 2/6인 모델, 공통 프로필/RNG | 기존 규칙·모션 회귀, 서버/표시 손·공·발 대조. 단일 경기 60Hz CPU/RSS 측정 |
| B. 로컬 온라인 1대1 | 독립 브라우저 2개, 고정 슬롯, 예측/보간, 공/점수/동작 | 이동→돌파→슛→블록→리바운드→공격권 전환→자연 종료. 양쪽 결과 일치 |
| C. 계정·자동 매칭 | 참가권·외형, 대기·취소·준비·중복 방지, 재접속·세션 철회·결과 | 실제 계정 2개 매칭. 취소/예약 경쟁·중복 탭·재시작 시험. XP/코인 불변 |

| F. Render 3대3 시험 공개 | 6인 부하·장기 이탈·혼잡, 모바일 팀 화면, 1대1과 수용 슬롯 공유 | 3대3 자연 종료와 1대1 회귀. Free 자원/대역폭이 감당될 때 메뉴 활성화 |

**1대1 완성의 범위는 A~D다.** 접속만 되는 시제품을 완성으로 보고하지 않는다. 3대3은 E~F이며 단순 인원 변경으로 끝나지 않는다. A단계 결합도·성능 확인 전에는 개발 일수를 약속하지 않는다.

재사용: 계정·참가권·외형·프로필, 접속·대기 상태, 방 수용량, 입력/상태/사건, 점수·소유권, 재접속·결과 저장.

3대3 추가: 팀 배정·고정 선수, 방향별 패스 대상·수신 안내, 패스/가로채기·6인 충돌·동시 블록/리바운드·박스아웃, 팀 카메라·모바일 HUD. Q는 패스, 기존 E의 AI 선수 전환은 온라인에서 사용하지 않는다. 수신 동작이 사람 동료의 이동을 과도하게 잠그지 않도록 별도 시험한다.

## 11. 검증과 성능 목표

- 규칙: 공 소유자 최대 1명, 사건별 득점 1회, 공격 제한/클리어/아웃/동점/종료 전 릴리즈, 동시 스틸·리바운드의 단일 결과.
- 실제 표시: 서버/화면의 손바닥·공 릴리즈/블록/캐치, 신발·관절의 디딤/착지. 진단 로그와 실제 화면을 함께 기록.
- 네트워크: RTT 50/100/150/250ms, 지터 20/50ms, 패킷 손실 1/3%. TCP 재전송 지연·버퍼·보정 튐·입력 누락을 따로 기록.
- 입력: 짧은 D·키업 유실·터치 취소·포커스 이탈/복귀·연속 행동·슛 타이밍.
- 권한/운영: 참가권 동시 소비·다른 모드·만료, 다른 슬롯 입력, 메시지 폭주/비정상 수치, 중복 탭, 세션 철회·옛 epoch, DB 실패·강제 재시작·배포·수용량 초과.
- 화면: 1280×800, 390×844, 844×390의 대기/경기/결과와 ko/en/ja/zh. 진행 중 사용자 프리뷰 탭 대신 별도 QA 탭 사용.

첫 목표는 단일 경기 60Hz 틱의 p95 실행 시간이 16.7ms 예산 안에 있고 15분 동안 누적 지연·메모리 증가가 없는 것이다. p99·CPU 스로틀링·전체 컨테이너 RSS도 함께 본다. 목표 미달을 숨기려고 틱이나 접촉 기준을 낮추지 않는다. 자원 여유 측정 전 동시 경기 수를 늘리지 않는다.

평균 스냅샷 2KiB를 가정하면 20Hz × 180초 × 6명은 스냅샷 송신만 약 42MiB/3대3 경기, 1대1 90초는 약 7MiB다. 입력·사건·프로토콜 오버헤드/재시도는 별도다. 실제 바이트를 측정하고 월 무료 경기 수로 단정하지 않는다.

가짜 클라이언트 부하는 처리량 확인용이고 사람의 실전·모션·모바일 렌더링 확인은 별도다. Android는 동일 WSS 계약을 쓰되 INTERNET 권한, 뒤로가기·앱 전환/복귀·실기기 연결을 따로 검증한다. Play 출시 완료로 기록하지 않는다.

## 12. 기존 Render 앱과 무료 운영

사용자가 다른 앱에서 Render Free를 사용 중이다. **같은 workspace에서는 월 750 무료 instance hours를 공유**한다. 코트러시에 별도 750시간이 주어진다고 계산하지 않고 배포 전 다른 서비스의 사용량·남은 시간·전송량을 확인한다.

코트러시용 별도 Free 서비스를 쓰되 외부 cron으로 상시 깨워두지 않는다. 유효한 대기/경기 중 ping은 연결 확인용이다. 서버 준비 중 기존 AI/연습은 사용할 수 있도록 하고 온라인 입장 때 현재 경기 종료를 안내한다.

Render Free의 임시 파일·재시작 조건을 반영해 영구 저장은 Supabase에 둔다. Free Postgres를 추가 생성하지 않는다. 자동 유료 전환은 전제하지 않고 사용량/지연 한계가 드러나면 실측값으로 다음 호스팅을 검토한다.

boot ID·접속/활성 경기 수·틱 시간·RSS·RTT·송신 바이트·인증/재접속 실패 코드만 필요한 범위에서 관찰한다. 비밀번호·복구 코드·참가권·토큰·내부 로그인 별칭을 로그에 남기지 않는다.
